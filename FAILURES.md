## 2026-10-21 · Part 10: Cursor Security found 2 ways a bearer token could reach AWS logs (both reproduced from the code, both fixed)
- **WAF request samples kept the Authorization header.** I had redacted the header in WAF *logs*, and the comment said a token "never reaches the log". But sampling was on for the ACL and both rules, and AWS does not apply logging redaction to sampled requests. So anyone with `wafv2:GetSampledRequests`, a common read-only permission, could read live tokens. **Fix:** sampling off everywhere (metrics stay on). **Test:** a `terraform test` assertion over every `visibility_config`. It fails with sampling turned back on for a single rule (checked).
- **The documented admin path printed the token into CloudWatch.** `auth issue` prints the new token, and the admin task's stdout goes to the app log group, kept 400 days. A token meant to be shown once would have been kept for longer than it is valid, readable by anyone with log read access. **Fix (in the kit, so both domains have it):** `issue --sha256 <hex>` registers the hash of a token the operator made on their own machine. It prints only the token ID. The README's admin step uses it and says never to run plain `issue` in the admin task. Registering a hash that is already in the file is now refused before writing. A duplicate would have made the whole file refuse every token. **Tests:** registration prints neither the token nor the hash, and the token verifies; a duplicate is refused and the file is unchanged (this one fails without the check, checked); a malformed hash is refused and nothing is written.
- **Lesson:** "the secret never reaches the log" has to be checked for every channel that sees the request or the output: samples as well as logs, and the stdout of a task as well as the server's own output. It is Part 9's minimisation lesson (test what the consumer reads) applied to infrastructure.

## 2026-10-20 · Part 9: Cursor Bugbot found 3 defects and Cursor Security 1 (all reproduced, all fixed)
- **A malformed JWT revocation file became a 500.** With `{"version": 1, "revoked": null}`, `RevocationList.read` raised `TypeError`, which the re-read did not catch, so `verify_token` threw instead of refusing. It is the same class as the empty-JWKS bug I had already fixed: each re-read caught a list of *expected* exceptions. **Fix:** `revoked` must be a list, and every re-read (tokens file, revocation file, JWKS file, JWKS URL) now refuses on *any* exception, logged. Guessing the list was the root cause. **Tests:** four malformed revocation files, and a tokens re-read that raises an unanticipated `TypeError`. Both failed on the old code (checked).
- **A save that failed after the rename lost track of the write.** `atomic_write` fsyncs the folder *after* `os.replace`. **Reproduced:** with the folder fsync failing, the caller was told "nothing was changed" and memory agreed, but the file held the booking, and a restart showed it. **Fix:** when the save raises, the file is read back. If it already holds the new ciphertext, the write is kept and reported as done (logged as not confirmed durable). Otherwise it is undone as before. **Test:** the folder fsync fails; the booking is reported, is in memory, and survives a reopen. It failed on the old code (checked).
- **Cursor Security Reviewer: a JWKS outage kept retired keys valid forever.** Every failed fetch still moved `_fetched_at` forward, so the cache never went stale, and a key retired (or compromised) during a lasting outage kept verifying. My own test had pinned that behaviour as "keeps the cached keys", and my design note above claimed a 5-minute bound the code did not have. **Fix:** track the last *successful* fetch. While fetches fail, retry every 30 s and keep the last good keys for at most an hour after that fetch; then refuse every JWT until a fetch succeeds. **Test:** an endpoint answers garbage for an hour. Tokens verify throughout, with retries; they are refused after the hour, and accepted again once it recovers. It fails on the old code (checked).
- **Cursor Bugbot, on my JWKS fix: every request fetched while the cache was empty.** To retry after 30 s I backdated `_fetched_at`, but the "unknown key ID" check reads the same timestamp and was then already due. With the endpoint down and no cached keys (a cold start, or after the one-hour drop), every verification did a blocking fetch under the lock. **Reproduced:** 10 verifications at one instant made 10 fetches. **Fix:** `_fetched_at` is the real time of the last attempt, and a separate `_refresh_after` is 5 minutes after a success and 30 s after a failure. **Test:** 10 verifications make 1 fetch, the next comes at 30 s and not at 29. It fails on the previous commit (checked). One clock meaning two things was the root cause.
- **Lesson:** "save or undo" has three outcomes, not two. A failure after the point of no return is a success that is not yet confirmed. I had learnt that for FHIR writes in Part 7, and missed it again for a local file.

## 2026-10-20 · Part 9: design choices I made where a safeguard can fail either way
- **A broken tokens file refuses every token.** The alternative was to keep the last good set. But the edit that broke the file may itself be a revocation, so keeping the old set would skip it. A typo can now cause an outage, never a skipped revocation. The JWT revocation file and the JWKS file behave the same way. A JWKS *URL* that cannot be reached keeps its last good keys, retrying every 30 s, for at most an hour after they were fetched: an outage at the authorization server should not become one here at once, nor keep a retired key alive. (My first version claimed "until they go stale (5 minutes)" but in fact kept them forever; see the Cursor Security entry above.)
- **An audit record that cannot be written stops the server, not the call.** The call has already happened (a booking cannot be un-sent), so reporting it as failed would be false. This is the Part 7 lesson about "timed out" versus "failed". The call returns its real result, and every later call is refused until the log works.
- **Encrypted SQLite is the database in memory, written back encrypted.** SQLCipher would need a native library. Field-level encryption would leave the schema, indexes and row counts in plaintext. Instead, each committed write that changed something re-encrypts the whole database (about 400 KB) and replaces the file atomically. That takes about 3 ms per booking here (measured). If the save fails, the in-memory database goes back to the last saved state and the call fails, so the caller, the memory and the disk always agree. The costs, stated in the README: one process per file, and a full rewrite per write.
- **The audit chain cannot detect truncation at the end.** No hash chain can without an anchor outside the file. `verify` prints the last sequence number and chain value so that an operator can record them elsewhere. The README says so.

## 2026-10-18 · Part 3: Codex review found 2x P1, 1x P2 (all reproduced, then fixed)

## 2026-10-18 · Part 2: Codex review found 2x P1, 3x P2 (all fixed)
Every bug finding was reproduced here before fixing, and each new test was checked by putting the bug back and watching the test fail.
- **P1 · A failed COMMIT wedged the store.** `COMMIT` sat outside the rollback path. With a file database and another connection holding a read lock, COMMIT failed ("database is locked") and left the transaction open, so every later write failed with "cannot start a transaction within a transaction". **Fix:** COMMIT is inside the `try`; any open transaction is rolled back before the lock is released; lock timeouts become `BusyError` ("busy, retry"). **Test:** a second connection holds a read lock; the booking fails cleanly, the slot stays open, the next booking succeeds.
- **P1 · The race tests never exercised `BEGIN IMMEDIATE`.** All racing calls shared one `Store`, so the Python lock serialized them; the test still passed with `BEGIN IMMEDIATE` removed. **Fix:** new races use separate `Store`s (separate connections) on one file: 8 patients for one slot, and one patient into 4 different slots at the same time (the unique index can't help there). Partial-overlap and back-to-back boundary tests added. **What the mutation showed:** with plain `BEGIN`, SQLite still prevented the double booking, but the losers got "database is locked" (read-to-write lock-upgrade deadlock) instead of a clear conflict. `BEGIN IMMEDIATE` makes them wait and then get "already booked".
- **P2 · Simultaneous first start crashed.** The "already seeded?" check ran before the write transaction, so two processes on a new file both tried to create the schema ("table specialties already exists"). **Fix:** the check runs inside `BEGIN IMMEDIATE`. **Test:** 6 concurrent constructors, no errors, seeded exactly once.
- **P2 · `APT-100000` could be booked but not cancelled.** IDs are zero-padded to *at least* 5 digits; the input pattern required *exactly* 5. **Fix:** pattern `APT-[0-9]{5,18}`. **Test:** fast-forward the sequence, book, cancel.
- **P2 · Extreme dates crashed with a generic error.** `9999-12-31` overflowed date arithmetic. **Fix:** dates must fall in 2000-01-01..2100-12-31, with a clear message. **Test:** three extreme inputs give a `ToolError` that isn't a crash.
- **Lesson:** my own race test proved the lock but not the transaction mode, and I described it as if it covered both. Concurrency tests need to use the same kind of connections production uses.
